## Purpose

Turn a set of PlantUML C4 diagrams into one portable SVG that is its own viewer: switching between levels, drilling down, sizing, hiding notes, and highlighting or pinning the paths a reader is following, all working in a browser with no server and no external assets.

The purpose has two halves. The Go side is a converter that assembles the file. The embedded script is the viewer that the file becomes. The converter exists to ship the viewer. Judged against that, about 400 of the 852 lines in `main.go` serve the purpose. The rest serves a second purpose that arrived in 0.5.0: driving Claude Code to author the diagrams in the first place. The most consequential finding is that the binary now has two purposes, and the second one has nothing to do with SVG or viewing.

## Structure

One Go package, one file. Control flow is: parse arguments, then either the `prompt` path (gather project context, build a text prompt, shell out to `claude`, then stack whatever appeared in `docs/c4/`) or the stacking path (optionally shell out to `plantuml`, load SVGs, parse, clean, pretty-print, template into one document, write). A 357-line `navigation.js` is embedded verbatim and holds the viewer: level switching, resizing, note hiding, path hover, pinned and multi-selection.

The core data is a short ordered sequence of at most four levels. The code models it three separate ways: a `0[1-4]-` filename regex when discovering `.puml` files, substring matching on "context", "container", "component", "code" when discovering `.svg` files, and a hard-coded `levels` slice inside the template builder. The README documents only the numeric convention. One ordered table should be the single source for all three.

The XML is handled by three different parsers on the same document: regexes pull `viewBox`, `width` and `height` off the opening tag, string indexing slices out the body, and `encoding/xml` is used twice, once to validate and once to pretty-print. The pretty-printer already tokenises the entire document, so it already has the `<svg>` start element and every attribute in hand. The two "fixes xml parsing issue" and "xlink mangling" commits in the history are the cost of rewriting XML with regexes.

`SVGStacker` is a mutable pipeline object rather than a pipeline. It overwrites its own `inputDir` with the temp directory mid-run, and half its methods do not read the receiver at all. Argument parsing signals subcommands by returning sentinel errors whose message text is then switched on. Both are opacity the purpose has not paid for.

The viewer script does two kinds of work that are not separated. One kind must happen at runtime because it depends on layout: measuring label bounding boxes with `getBBox`, resizing to the viewport, showing and hiding layers, toggling classes. The other kind is static rewriting of the document that could have been done once by the converter: stripping `<title>` elements, identifying which groups are notes by their fill colour, identifying which links attach to notes by ID substring. The static work is done in JS, at load, and again on every level switch. `setupLinkHoverEnhancements` inserts a fresh hitbox and background rectangle per link and registers a fresh `document` keydown listener per link each time `showLevel` runs, so nodes and listeners accumulate as the reader moves between levels. This is the one defect in the part of the project that is the product.

Smaller vestiges: the "diagram not found" placeholder layer is built for every missing level but can never be shown, because navigation only iterates existing levels. `copyTestdataFiles` and the `testdata/` directory are never used. `CLAUDE.md` still describes a Node implementation, a hard-coded PlantUML path, and an `output/` directory that no longer exist.

## Growth

Traced per commit, the converter core has sat between 300 and 400 lines since the Go migration. The two large jumps in `main.go` were "more unix like" (about 290 lines, mostly CLI handling and a CSS-only mode later deleted) and "add prompt command" (about 210 lines plus a 209-line spec embedded into the binary). Neither is the purpose. The Go side is growing toward being a Claude launcher, and the existing `TODO.md` entry to replace that integration with a skill is the right first pruning.

`navigation.js` has almost tripled, from 128 to 357 lines, and every increment was a viewer feature: fit mode, note toggling, hover highlighting, persistent selection, multi-select, Escape handling. That growth is toward the purpose and is healthy in direction. Its shape is the concern: each feature was added as more runtime DOM work inside the same load-and-switch path, without a boundary between what the converter should prepare and what the viewer must do live. The accumulation defect is the first symptom of that missing boundary, and further viewer features will make it worse unless the boundary is drawn.

## Proposed architecture

Two pure functions, one in Go and one in JS, with the converter doing everything static and the viewer doing only what depends on layout. This is a rewrite of `main.go` and a restructuring of `navigation.js`, not a refactor of either.

- **One level table.** A package-level ordered list pairing numeric prefix with level name, for example `01` with `context`. Diagram discovery, button order, layer order and the injected `availableLevels` array all derive from it. The filename regex, the substring matcher and the inline `levels` slice go.
- **One `Diagram` value.** Level, viewBox, width, height, body. Produced by one function that tokenises the source once with `encoding/xml`, reads the dimensions from the `<svg>` start element, drops `<script>` and `<title>` tokens, rewrites the `<a>` wrapper into an `onclick` on the enclosing group, tags note groups and note-attached links with a class, and re-encodes indented. One parser replaces three, and the regex-on-XML bug class disappears with them.
- **One template.** `stack(title, []Diagram) string` renders a single `text/template` holding the CSS, buttons, layers and script. `SVGStacker` and its mutable fields are deleted. PlantUML rendering becomes `render(dir) (paths, cleanup, error)` called once from `main`.
- **`flag` for the CLI.** Delete `parseArgsSlice` and the error-string dispatch. The remaining interface is a directory, `--output` and `--title`.
- **Viewer does only runtime work, once.** With titles stripped and notes tagged by the converter, the script no longer searches for fill colours or ID substrings. What remains is layout-dependent: `getBBox` hitboxes, resize, show and hide, class toggling, and the selection state. Hitbox creation runs once per layer at load, the Escape listener is registered once on `document`, and `showLevel` only toggles visibility. The viewer features stay; the accumulation goes.

What this removes, roughly: `main.go` from 852 to around 400 lines, the embedded spec, the `testdata/` directory, and the `SVGStacker`, `ProjectContext` and `DiagramInfo` types collapsed to one. `navigation.js` loses its static-rewriting code but keeps every feature. What it sharpens: the binary becomes exactly a converter, the script becomes exactly a viewer, and the seam between them is a small set of classes the converter promises to emit and the viewer promises to read.

## Reductions

- **Cut the `prompt` subcommand** and its `gatherProjectContext`. Keep `C4-DIAGRAM-SPEC.md` in the repository as documentation or skill material, but stop embedding it. This is already planned in `TODO.md`. Agree, and do it first.
- **Delete the placeholder layer** branch in the layer builder. It is unreachable.
- **Delete `copyTestdataFiles` and `testdata/`.** Nothing calls them.
- **Collapse the three XML parsers** into the one token pass described above.
- **Collapse the three level conventions** into the one table.
- **Move static DOM rewriting out of the viewer** into the converter, and make the remaining runtime enhancement run once per layer. No viewer feature is a candidate for removal; they are the product.
- **Rewrite `CLAUDE.md`** or delete it. It describes a project that no longer exists.

## Tests and performance

The suite has seven tests, all of them against the converter. Two of them, `TestGeneratedSVGIsValidXMLStreaming` and `TestActualGeneratedFiles`, are the same test twice. Four in total reduce to "the output is well-formed XML". `ValidateXML`, `titleCase` and `extractLevel` are tested directly and are trivial. The transformation that makes drill-down work, turning a PlantUML `$link` into an `onclick` on the right group, has no test that checks the `onclick` is present. Neither dimension extraction nor the injected `diagramData` block is tested.

The viewer, which is the purpose, has no tests at all. Level switching, sizing modes, note toggling, hover and pinned selection are exercised only by opening the file in a browser. The accumulation defect above is exactly the kind of regression such a test would have caught. The proposed split makes this tractable: with the converter emitting a small, stable set of classes and IDs, the viewer becomes a script over a known document shape that can be loaded into any DOM implementation and driven by calling `showLevel`, `toggleNotes` and the click handlers directly, then asserting on classes and node counts. That is the single largest testing gap in the project.

On the converter side the structural blocker is that output is not deterministic: the metadata block embeds `time.Now()`, so a golden-file test against a checked-in expected output is impossible. Make the timestamp injectable, or drop it, and the whole converter becomes one golden test per example directory. The proposed pure `stack` function makes that test a one-liner and would replace most of the current suite.

Performance is not an architectural concern at this size. The one shape-level issue is the runtime accumulation already described, and the proposed boundary removes it rather than patching it.
